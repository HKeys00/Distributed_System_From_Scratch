- Planned my architecture for my basic node set up 
- The architecture involves requests flowing towards a controller on the ASP.NET node I've set up, this controller will then try to place that request on the Ingress queue, this queue has a set max length to avoid the node being overwhelmed with requests, if there's not room on the queue the controller responds with a 429 error code or 202 status code if the task was added to the queue, I used a channel as my queue because it works very well for the publisher consumer pattern I'm setting up

- The retriable-view design had a real problem: a task in retry would match both the retry view AND the stale view. Relay polls both, publishes twice. Exact failure mode the invariants are supposed to catch.
- Root cause: trying to partition a 2D state space (broker-confirmed? worker-finished?) into 3 non-overlapping views. Doesn't work, regions overlap.
- Fix: explicit `nextAttemptAt` column on tasks. Outbox view becomes "sentAt null AND retry_count < 5 AND nextAttemptAt <= now() AND no success row". Brand new tasks, retry-after-failure, and scheduled tasks all collapse into the same view membership. Phase 3 scheduling falls out for free.

- Reaper failure transaction (when retries hit 5): insert into DLQ, set terminal flag on task, all atomic. Otherwise: republish, increment retries, update sentAt.
- Stale view needs an "attempt-scoped no conflict" clause — naive `NOT EXISTS conflict` excludes any task that's ever failed even if currently in-flight on a later attempt. Solution: `attempt` column on conflicts matching retry_count at time of failure, stale view checks `NOT EXISTS conflict WHERE attempt = current retry_count`.

08/05/26
- Sat down and worked through the rate limiter design properly. Started with blocking-sleep ("wait until token available") which is the obvious wrong answer — worker sleeps holding the message, broker doesn't redeliver, throughput collapses to the rate limit even on a multi-domain workload.
- The real model: deferral, not blocking. Worker tries to get a token, if no token compute next-token-time, update nextAttemptAt to that time + jitter, null sentAt, ack broker, done. Task goes back to the outbox view and gets re-dispatched when eligible. Worker never blocks.
- Critical distinction: deferral is NOT a retry. Nothing failed. Don't write a conflict, don't increment attempts. Different code path from the failure path.
- Almost screwed this up — was about to make rate-limit hits just go through the existing retry mechanism. Would have meant: false DLQs (task DLQ'd after 5 deferrals having never been fetched), retry metrics polluted, conflict table filled with non-conflicts, backoff math wrong (90s wait for a token that was available in 1s). Glad I caught this before implementing.
- Two layers of rate-limit handling: before fetch, no token → deferral (no failure recorded). During fetch, 429 from target → real retry (write conflict, increment attempt, exponential backoff). Different layers, different mechanisms.

09/05/26
- Discovered the relay was still incrementing attempt on publish. This was fine when "publish" and "retry" were the same thing but now with deferrals, every defer-and-redispatch was ticking attempts up. Tasks were hitting DLQ after 5 deferrals having never been fetched.
- Refactor: relay just publishes and sets sentAt. It doesn't know or care about retry semantics. The attempt counter is incremented in exactly three places now: worker on failure (with conflict), reaper on presumed-dead (with synthetic conflict), worker on token-acquired (start of actual fetch attempt).
- Wait, three places is still wrong — incrementing on token-acquired conflicts with "attempt == count(conflicts)" because the increment happens before the conflict. Need to think about whether to increment at start of attempt or only on failure.
- Resolution: attempt is incremented in the same transaction as the conflict insert (worker failure path) or synthetic conflict insert (reaper presumed-dead path). It is NOT incremented at the start of an attempt. Means the strengthened invariant holds: attempts always equals count(conflicts).
- This makes "what attempt is this task currently on?" slightly different from "how many times has this been tried?" The first attempt has attempts=0 and no conflicts. After it fails, attempts=1 and one conflict. The number stored is "how many failures so far", and the current attempt is attempts+1.
- Once I had that mental model straight, the chaos harness assertion `SELECT WHERE attempts != count(conflicts)` returned zero rows on every run. Good.

  Session lock scope — the model                                                                                                                            
   
  A session-level advisory lock has two pieces of "scope":                                                                                                  
                                                                                                                                                          
  1. What it identifies — you pass a bigint key (or two ints). That number is the entire identity of the lock. Postgres doesn't know it represents "leader  
  election" — that's just convention between clients. All three relay replicas have to agree on the same number (e.g., a hash of the string "relay_leader",
  or just a constant like 0xRELAY01). Pick wrong/different numbers and the locks don't collide.                                                             
  2. Who holds it — the session. Not the transaction, not the connection-pool slot, not the C# NpgsqlConnection object — the actual physical Postgres     
  backend process. The lock lives in shared memory keyed by that backend's PID.                                                                             
   
  That's the entire scope. Lifecycle is:                                                                                                                    
                                                                                                                                                          
  - SELECT pg_try_advisory_lock(K) returns true → this session now holds K.                                                                                 
  - The session goes away (clean close, killed via pg_terminate_backend, network drop eventually detected) → K is released automatically.
  - SELECT pg_advisory_unlock(K) → explicitly released, session keeps going.                                                                                
                                                                                                                                                          
  Two important properties:                                                                                                                                 
                                                                                                                                                          
  - Re-entrant. Same session can grab the same K many times; you have to unlock it the same number of times (or let the session die). Postgres tracks the   
  count.                                                                                                                                                  
  - Pooling kills it. If you grab a session lock on a connection from a pool, when the pool returns the connection, DISCARD ALL runs and releases all       
  session-level advisory locks. That's exactly why the LISTEN connection in Worker.cs:82 is the only safe place to hold one in this project — it's not      
  pooled, it lives for the lifetime of ExecuteAsync.
                                                                                                                                                            
  What this means concretely for your design                                                                                                                
   
  The leader-election lock has to be acquired on the LISTEN connection. Same NpgsqlConnection object. Same physical session. The heartbeat UPDATE also runs 
  on that same connection. Why?                                                                                                                           
                                                                                                                                                            
  - If the heartbeat is on the LISTEN connection, then "heartbeat succeeded" ↔ "session is alive" ↔ "I still hold the lock." One indivisible fact.          
  - If the heartbeat runs through a pooled DbContext, you've decoupled them. The pooled connection might be fine while the LISTEN session has died — your
  heartbeat keeps writing and you don't realize you've lost leadership.                                                                                     
                                                                                                                                                          
  So: same connection holds the LISTEN, holds the advisory lock, runs the heartbeat UPDATEs. ⏺ Sharp question. Walk through it carefully:                                                                                                                
                                                                                                                                                            
  What happens to A's PID after the kill                                                                                                                    
                                                                                                                                                            
  pg_terminate_backend(100) terminates the Postgres backend process serving A's session. That OS process exits. From that moment on, "PID 100" doesn't refer
   to A's Postgres session anymore — that session simply doesn't exist.                                                                                     
                                                                                                                                                            
  When A wakes up from its pause, what state is it in?                                                                                                    

  - Its C# NpgsqlConnection object is still there.                                                                                                          
  - The underlying socket is broken (server side hung up).
  - The first DB call A attempts after waking up will throw — Npgsql gets EOF / RST on the socket.                                                          
  - If A's code catches that and reconnects, the reconnect opens a brand new session with a new PID (say 300). A's old PID 100 is gone forever.             
                                                                                                                                                            
  So when C eventually calls pg_terminate_backend(100), it does not hit A's new session. A's new session is PID 300. C is targeting a number that no longer 
  corresponds to A.                                                                                                                                         
                                                                                                                                                            
  But — here's the subtle problem                                                                                                                         

  OS PIDs get reused. After PID 100's process exits, the kernel will eventually assign 100 to some completely different process. That process could be:     
   
  - Another Postgres backend for some unrelated client (Controllers, Worker_Node, even A's own reconnect on a different code path).                         
  - A non-Postgres process (less concerning — pg_terminate_backend only operates on Postgres backends and just returns false if the PID isn't a backend). 
                                                                                                                                                            
  The case that actually bites: PID 100 is reused for an innocent Postgres backend belonging to some other service. C's stale-view kill takes out a healthy,
   unrelated session.                                                                                                                                       
                                                                                                                                                            
  So the failure mode you should worry about isn't "C kills A again" — it's "C kills a stranger."                                                           
   
  Defense                                                                                                                                                   
                                                                                                                                                          
  What's the cheapest way to make C not act on stale information? You have two options:                                                                     
   
  1. Re-read right before acting. C polled the row 30 seconds ago and decided to take over. Before calling pg_terminate_backend, re-read the row inside the 
  same transaction. If the timestamp is now fresh, abort — somebody else already became leader. If the PID changed, also abort.                           
  2. Don't kill unless you have to. Try pg_try_advisory_lock(K) first. If it succeeds, the previous holder's session is already dead (likely from TCP       
  keepalive eventually noticing). You didn't need to kill anyone — just take it. If it fails, then fall back to the kill path.                              
   
  Option 2 has a nice property: you only ever issue pg_terminate_backend when the lock is actually still held server-side, which dramatically narrows the   
  window for harming a stranger.                                                                                                                          
                                                                                                                                                            
  Both can be combined: try_advisory_lock first; on failure, re-read the row, check both timestamp staleness and PID consistency, then kill.                
   
  Sanity check                                                                                                                                              
                                                                                                                                                          
  Trace through your original three-node scenario again with option 2:                                                                                      
                                                                                                                                                          
  - A leader, paused.                                                                                                                                       
  - B detects stale, calls pg_try_advisory_lock → fails (A's session still alive server-side). B reads row, sees stale timestamp + PID 100. B kills 100,
  tries lock again, gets it, becomes leader, updates row.                                                                                                   
  - C, with its stale view of PID 100, finally acts. C calls pg_try_advisory_lock → fails (B holds it). C reads row → sees fresh timestamp, PID 200. Aborts.
   No kill issued.                                                                                                                                          
                                                                                                                                                          
  PID-reuse risk avoided entirely because C never gets to the kill step.                                                                                    
                                                                                                                                                          
  So: the answer to your literal question is "A's new PID is different, so C wouldn't re-kill A specifically — but C could kill someone else who got A's old
   PID, unless you guard against acting on stale state." Want to revise your sketch with these guards?
