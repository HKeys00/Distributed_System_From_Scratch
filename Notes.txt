26/03/26
- Planned my architecture for my basic node set up 
- The architecture involves requests flowing towards a controller on the ASP.NET node I've set up, this controller will then try to place that request on the Ingress queue, this queue has a set max length to avoid the node being overwhelmed with requests, if there's not room on the queue the controller responds with a 429 error code or 202 status code if the task was added to the queue, I used a channel as my queue because it works very well for the publisher consumer pattern I'm setting up
- Next I created a work item dispatcher which will monitor this queue and then based on the execution type (CPU or IO bound) will pass that work item to the respective CPU bound or IO bound worker queue, these queues have different size constraints due to the nature of the work they perform. 
- If the dispatcher attempts to pass this work item to a queue that is full, the request will be dropped and logged, this isn't a permanent solution but for simplicity that what I've gone for for the time being.
- The whole system lives in process — channels are in-memory, workers are tasks on the same node. Fine as a starting point but no durability story; a crash drops every in-flight request on the floor.
- Already smelling the limits: the 429 on a full queue is honest, but "drop and log" on the dispatcher's full worker queue is silent data loss for accepted work. The 202 is starting to feel like a lie.

- Working through the worker's completion path — same transactional outbox discipline as submit, but mirrored
- Worker has to: insert success row, insert N child tasks (each with own idempotency key), update parent task state. All three in one DB transaction. Broker ack happens AFTER commit.

- The retriable-view design had a real problem: a task in retry would match both the retry view AND the stale view. Relay polls both, publishes twice. Exact failure mode the invariants are supposed to catch.
- Root cause: trying to partition a 2D state space (broker-confirmed? worker-finished?) into 3 non-overlapping views. Doesn't work, regions overlap.
- Fix: explicit `nextAttemptAt` column on tasks. Outbox view becomes "sentAt null AND retry_count < 5 AND nextAttemptAt <= now() AND no success row". Brand new tasks, retry-after-failure, and scheduled tasks all collapse into the same view membership. Phase 3 scheduling falls out for free.
- Stale view shrinks to one job: detect dead workers. Single threshold, doesn't scale with retries. Tuned to "longer than longest realistic crawl" — has to dominate the per-domain rate limit wait.
- Worker failure transaction: insert conflict row, increment retry_count on task, set nextAttemptAt = now() + backoff(retry_count), null sentAt. All atomic. Outbox picks it up after backoff window.
- Reaper failure transaction (when retries hit 5): insert into DLQ, set terminal flag on task, all atomic. Otherwise: republish, increment retries, update sentAt.
- Stale view needs an "attempt-scoped no conflict" clause — naive `NOT EXISTS conflict` excludes any task that's ever failed even if currently in-flight on a later attempt. Solution: `attempt` column on conflicts matching retry_count at time of failure, stale view checks `NOT EXISTS conflict WHERE attempt = current retry_count`.
- State machine is now non-overlapping: pending publish (in outbox), in-flight (sentAt set, no conflict for current attempt, not yet stale), presumed-dead (in stale view), just-failed (back in outbox via nextAttemptAt), terminal success, terminal failure. Every task in exactly one state.
- Lost-publish detection: stale view catches it for free, treated as a dead worker, retried. Incorrect framing but correct behaviour. Phase 2 will fix properly with publisher confirms.

08/05/26
- Sat down and worked through the rate limiter design properly. Started with blocking-sleep ("wait until token available") which is the obvious wrong answer — worker sleeps holding the message, broker doesn't redeliver, throughput collapses to the rate limit even on a multi-domain workload.
- The real model: deferral, not blocking. Worker tries to get a token, if no token compute next-token-time, update nextAttemptAt to that time + jitter, null sentAt, ack broker, done. Task goes back to the outbox view and gets re-dispatched when eligible. Worker never blocks.
- Critical distinction: deferral is NOT a retry. Nothing failed. Don't write a conflict, don't increment attempts. Different code path from the failure path.
- Almost screwed this up — was about to make rate-limit hits just go through the existing retry mechanism. Would have meant: false DLQs (task DLQ'd after 5 deferrals having never been fetched), retry metrics polluted, conflict table filled with non-conflicts, backoff math wrong (90s wait for a token that was available in 1s). Glad I caught this before implementing.
- Two layers of rate-limit handling: before fetch, no token → deferral (no failure recorded). During fetch, 429 from target → real retry (write conflict, increment attempt, exponential backoff). Different layers, different mechanisms.

09/05/26
- Discovered the relay was still incrementing attempt on publish. This was fine when "publish" and "retry" were the same thing but now with deferrals, every defer-and-redispatch was ticking attempts up. Tasks were hitting DLQ after 5 deferrals having never been fetched.
- Refactor: relay just publishes and sets sentAt. It doesn't know or care about retry semantics. The attempt counter is incremented in exactly three places now: worker on failure (with conflict), reaper on presumed-dead (with synthetic conflict), worker on token-acquired (start of actual fetch attempt).
- Wait, three places is still wrong — incrementing on token-acquired conflicts with "attempt == count(conflicts)" because the increment happens before the conflict. Need to think about whether to increment at start of attempt or only on failure.
- Resolution: attempt is incremented in the same transaction as the conflict insert (worker failure path) or synthetic conflict insert (reaper presumed-dead path). It is NOT incremented at the start of an attempt. Means the strengthened invariant holds: attempts always equals count(conflicts).
- This makes "what attempt is this task currently on?" slightly different from "how many times has this been tried?" The first attempt has attempts=0 and no conflicts. After it fails, attempts=1 and one conflict. The number stored is "how many failures so far", and the current attempt is attempts+1.
- Once I had that mental model straight, the chaos harness assertion `SELECT WHERE attempts != count(conflicts)` returned zero rows on every run. Good.
